## Context

漏脱敏帧已经算在 `_compute_desensitization` 的 `rows` 里，每行有 `src_frame`、`dst_frame`、`src_faces`、`dst_faces`。结果框只把前 20 行拼成纯文本。Word 报告另有全量明细，本次不改。

两个预览是 `VideoView`。拖进度条对有索引的 mp4 走 `cap.set`，经常停在附近关键帧。裸码流才走 `decode_seek` 的顺序解码。播放器没有对外的「跳到第 N 帧」。后台线程只往显示队列放帧，主线程 `_render_tick` 取帧画画面，并按该帧更新时间和进度条。

右侧栏写死 320 像素，包在一层 Canvas 里整体滚动。窗口默认 1120×720。

## Goals / Non-Goals

**Goals:**

- 检测成功后，右侧列出本次全部漏脱敏帧，可滚动、可单击。
- 单击后两边暂停，时间和进度条立刻到目标帧，画面显示「加载中」，并精确停在列表写出的帧号上。
- 再点另一行、重新检测或重新导入时，取消尚未完成的跳转。

**Non-Goals:**

- 不改脱敏率公式、对齐公式和 Word 报告。
- 不改进度条拖动的跳转方式。进度条仍可对 mp4 使用 `cap.set`。
- 不对齐越界、没有脱敏帧号的记录不进列表。

## Decisions

### 1. 列表放在右侧栏底部，不放进现有 Canvas

右侧栏从 320 改为 460，窗口默认改为 1280×720。统计、公式和结果框仍在上方 Canvas 里。漏帧列表 pack 在右侧栏底部并占满剩余高度，自带滚动条。

这样列表高度跟着窗口走。若把列表再塞进 Canvas，内部控件拿不到剩余高度，滚轮也会和外侧滚动抢。

一行文本为 `00:10 原帧250 → 00:06 脱敏帧90  2/1`。时间用现有的时分秒。帧号和人脸数来自该行，不从文本反解析。列表项旁另存 `src_frame` 与 `dst_frame`。

空列表时标题为「漏脱敏帧」，列表区域写「未发现漏脱敏帧」。有记录时标题为「漏脱敏帧（N）」。结果框不再拼漏帧文字，也不再写「全部人脸帧均已脱敏」。

### 2. `VideoView` 增加公开的精确跳转

脱敏 UI 只调用公开方法，例如 `show_frame(frame_idx)`，不写 `_seek_pending`、`_seek_gen`。该方法在主线程完成这些事：暂停播放；代次加一，使上一跳失效；立刻改时间和进度条；清空画面并显示「加载中」；清掉显示队列里的旧帧。解码放在后台线程，沿用顺序解码：目标在当前帧之前则重开文件，从第 0 帧 `grab` 到目标。这次调用强制走该路径，即使文件有容器索引也不使用 `cap.set`。

解码线程不调用 Tk。帧进入现有显示队列，由 `_render_tick` 画出来。加载期间 `_render_tick` 不得用队列里的旧帧把时间和进度条改回去。代次不匹配的结果直接丢掉。

两边各调一次。谁先解码完，谁先撤掉「加载中」。

顺序解码得到的帧号可信，检测框继续用预处理缓存。这和现有「`cap.set` 之后不信帧号」的规则一致。

### 3. 取消只靠代次

新的 `show_frame`、重新导入、开始下一次检测，都让两路代次失效。画面保持「加载中」，直到当前这一跳的帧到达。用户在加载中拖动该路进度条时，这一次列表跳转作废，改由进度条自己的逻辑处理。

## Risks / Trade-offs

- [长视频往回跳要重开文件并逐帧丢掉] → 画面显示「加载中」，连点只保留最后一次。不在本次把进度条也改成精确跳转。
- [旧帧还在显示队列里，会盖掉「加载中」或把时间改回去] → 跳转开始时清空队列，加载完成前忽略旧帧对时间和进度条的更新。
- [解码线程直接动 Tk，会卡主界面] → 只入队，由已有的主线程定时器画画面。
- [右侧加宽后，最小窗口 900×600 上两个预览更窄] → 只改默认尺寸，不改最小尺寸。用户仍可拉大窗口。

## Migration Plan

无数据迁移。旧的检测结果在重新检测后才出现列表。

## Open Questions

无。列表内容、位置、行格式、精确帧号、加载中、连点取消和清空时机已在讨论中确定。
